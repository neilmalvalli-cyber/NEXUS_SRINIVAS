# Recorded results (Phase 4)

> **Historical record.** These numbers were measured during Phase 4, before
> the Prompt 10 changes (write-through moves, `check --no-repair`, key-sorted
> compaction). The re-run against the current code is in
> [validation/](validation/README.md); prefer it when the two differ. The
> latest full run (Prompt 12, including Torture Engine 2.0 and the benchmark)
> is in [final/](final/README.md).

All numbers below were measured on 2026-11-06 on the development machine, with
the code as it was at commit `8058c2d`. Nothing here is an estimate.

**Environment:** Windows 11 Home 10.0.26200, AMD Ryzen 7 5800H (8 cores / 16
threads), 32 GB RAM, WD PC SN810 512 GB NVMe SSD, Windows Defender real-time
protection **on**, Go 1.27.3 windows/amd64. Databases on the SSD (user temp
directory and the repository directory). Kills are `TerminateProcess`
(`os.Process.Kill`).

## Torture tool (judge invocations and extra modes)

`go build -o . ./src/cmd/kvdb ./src/cmd/torture` (the tool was in `./torture` until 2026-11-07), then:

| Command | Result | Acked writes | Rejected | Unknown | Notes | Time |
|---|---|---|---|---|---|---|
| `torture --iterations 500 --seed 12345` | **PASS 500/500** | 160,487 | 0 | 1,405 | 3 writers; a compaction request in flight at 296 kills; 6 recoveries completed an interrupted compaction (authority rule) | 169 s |
| `torture --iterations 100 --seed 999 --mode large-values` | **PASS 100/100** | 11,094 | 0 | 171 | values 256 KiB–1 MiB, half exactly 1 MiB; files up to ~17 MB | 86 s |
| `torture --iterations 100 --seed 7 --mode compaction` | **PASS 100/100** | 42,197 | 0 | 290 | compaction request in flight at 82 kills; 2 interrupted compactions resolved on reopen | 79 s |
| `torture --iterations 100 --seed 42 --mode recovery-crash` | **PASS 100/100** | 1,386 | 0 | 271 | 200,000-key database; 206 kills aimed at `kvdb open`, **147 landed while recovery was running** | 262 s |
| `torture --iterations 100 --seed 11 --mode disk-full` | **PASS 100/100** | 14,141 | **7,190 `full`** | 289 | `--max-bytes 262144`; every rejected write verified absent; file never above the cap | 63 s |
| `torture --iterations 100 --seed 13 --mode large-batch` | **PASS 100/100** | 143,637 | 0 | 277 | 10,000-op batches racing single writes | 187 s |

"Unknown" = a write that was sent but had no reply when the process died; the
oracle accepted it as fully present or fully absent, never partial. In every
iteration at least one write request was in flight at the kill (in
large-values mode 66 of 100, because 1 MiB requests are fewer).

**What the torture runs did not show:** none of these recoveries had to cut a
torn tail (`torn-tails=0`). A `TerminateProcess` almost never lands between two
`WriteFile` calls of one frame on this machine. Torn frames are therefore
proven by the in-process fault-injection scenarios (A2, A7, B1, B2, B6, F4),
not by the torture runs. See BREAKING.md §3.

**Mutation check (the oracle is not rigged):** a `kvdb` built to print `ACK`
before writing was caught at iteration 2–3; one that writes a batch as
separate frames was caught at iteration 1–3 (default and large-batch modes).

## Acceptance workload: 1,000,000 PUT then 1,000,000 DELETE

`KVDB_ACCEPTANCE=1 go test ./src/scenarios -run TestAcceptanceMillionPutDelete -v`
— every operation is a separate durable call (own frame, own `FlushFileBuffers`),
through the public API:

| Step | Measured | Result |
|---|---|---|
| 1,000,000 `Put` (key 10 B, value 41 B) | 6 min 15 s, 2,670 ops/s, 0.375 ms/op; file 93,000,032 B; peak heap 136 MiB | PASS |
| Reopen (recovery) with 1,000,000 keys | **687 ms** (limit 2 s); peak heap 105 MiB | **PASS** |
| 1,000,000 `Delete` | 6 min 22 s, 2,616 ops/s; file peaked at 101,745,032 B and was shrunk 9 times by automatic compaction; 1,161,382 B at the end; peak heap 280 MiB | PASS |
| Explicit `Compact` | 11 ms: 1,161,382 → **32 B** (largest file during the run 101,745,032 B) | **PASS** (file shrank) |
| 10,000 `Put` after compaction, reopen, verify | 3.7 s; 10,000 keys, values and full-file `Verify` OK; file 690,032 B | **PASS** |

Other 1,000,000-key recovery measurements: `TestGroupB/B6` (1M keys + torn
10,000-op batch) and `TestGroupF/F3` (1M keys written through `kvdb serve`,
process killed, `kvdb open` prints `recovery_ms`) — see SCENARIO_RESULTS.md.
